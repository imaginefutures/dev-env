# 일하는 방법

요청을 받아 끝내기까지의 순서다. 어느 프로젝트에나 쓰는 규칙만 둔다. 이 프로젝트에만 맞는 값(설계 문서, 층 순서, 부품, 데이터 규칙)은 [docs/project.md](docs/project.md)가 맡고, 둘이 부딪히면 project.md가 이긴다.

코드를 어떻게 짜는지는 [docs/code-rules.md](docs/code-rules.md), 서브에이전트로 나누고 합치는 법은 [docs/agents.md](docs/agents.md)다. 화면이 있는 프로젝트는 `docs/web.md`도 따른다.

```
요청 → 분류(설계 먼저 / 샘플 먼저 / 바로 개발) → 계획(가정·성공 기준) → 구현 → 확인 → 커밋(문서:·검증: 줄)
```

## 1. 요청을 분류한다

답변 첫머리에 어느 길인지 한 줄로 밝힌다.

| 요청 | 길 |
|---|---|
| 개념·구조·규칙이 바뀐다(데이터 구조, 모듈 경계, 용어) | 설계 먼저: 설계 문서(project.md에 적힌 곳)를 먼저 고치고 확인받는다 |
| 화면·문구(문구, 모양, 배치, 새 화면 시안) | 샘플 먼저: `docs/web.md` 1절 |
| 규칙·권한·계산·저장, 재현되는 오류, 마이그레이션·환경 변수, 문서·도구, 명백한 오타 | 바로 개발 |

- 애매하면 더 앞의 길(설계 먼저 → 샘플 먼저 → 바로 개발)로 간다. 사용자가 "바로 해"라고 하면 따른다.
- 돌려 보면 알 수 있는 갈림길은 묻지 않고 버릴 스크립트로 확인한다.

## 2. 계획을 적는다

- 계획은 답변 첫머리에 체크리스트로 쓴다. **가정**과 **성공 기준**(`단계 → 확인 방법`)을 적는다. 큰 작업은 어느 조각부터 끝낼지도 적는다.
- 결과가 갈릴 때만 묻는다. 권장안을 표시한 객관식으로 하나씩 묻고, 많으면 웹페이지(Artifact)로 모아 묻는다.
- 여러 기능에 걸친 질문은 사람이 지나가는 길을 코드에서 따라가고, 끊긴 곳도 적는다.
- 새 기능이 이미 있는 기능과 같은 일을 하게 되면 **대체 표**를 쓴다. 기존 흔적(화면·주소·표·문서)마다 운명을 적고 기본값은 삭제다. 둘을 같이 두는 것은 사용자 승인과 끝낼 조건이 있을 때만이다. 대체와 제거는 같은 커밋에서 한다.

## 3. 커밋

- 커밋은 주제 하나씩 나눈다. 일하는 방식·규칙 문서를 바꾸는 변경은 기능 커밋과 따로 한다.
- 본문에 아래 줄을 넣는다. 해당 없으면 `해당 없음 — <이유>`.

| 줄 | 쓰는 것 |
|---|---|
| `문서:` | 고친 문서 |
| `검증:` | 실제로 실행한 확인과 결과. 실행하지 않은 확인은 쓰지 않는다 |

- 커밋 전에 `git diff --cached`로 바뀐 줄마다 요청이나 대체 표로 설명되는지 본다. 설명 안 되는 줄은 뺀다.
- 문서가 설명하는 사실이 바뀌면 그 문서를 같은 커밋에서 고친다.
- 테스트를 돌리지 않았으면 안 돌렸다고 쓴다.

## 4. 확인받고 하는 일

아래는 하기 전에 바뀌는 내용(전/후)을 보여 주고 확정을 받는다. 나머지는 묻지 않고 한다.

- 일하는 방식을 바꾸는 문서·규칙 변경(`CLAUDE.md`, `CONTRIBUTING.md`, `docs/`, `.claude/`). 코드 변경에 맞춰 문장 한두 줄을 고치는 것은 뺀다.
- 마이그레이션, 환경 변수 변경, 데이터 삭제
- 파일 10개 이상을 지우거나 옮기는 정리
- 요청에 없던 것을 함께 바꾸게 된 경우

운영 환경과 데이터:

- 운영 데이터를 고치거나 지우는 일은 백업하거나 대상 건수를 미리 보여 준 뒤 확인받고 한다.
- 외부 발송(문자·메일·알림)은 대상과 문구를 확인받은 뒤 보내고, 가능하면 소수에게 먼저 보낸다.
- 시험 환경에는 실제 발송·결제 키를 넣지 않는다.
- 운영 데이터 사본은 git이 무시하는 폴더(`temp/`)에만 둔다. 개인정보가 든 파일(엑셀·CSV·덤프·`.env`·개인키)은 커밋하지 않는다.
- 이 프로젝트에서 더 지킬 것은 project.md에 있다.

## 5. 여러 세션이 같은 저장소를 쓴다

- 이 대화에서 고친 파일과 `git status`를 비교한다. 기억 없는 변경은 남의 것이다. 답을 듣기 전에는 남의 변경을 커밋하지 않는다.
- 커밋 직전에 `git diff --cached --stat`로 남이 `git add`한 파일이 딸려 오지 않았는지 본다. 뺐으면 한 줄로 알린다.
- push 전에 `git log origin/<브랜치>..HEAD`로 나갈 커밋을 본다. 이 대화에서 만들지 않은 커밋이 섞였으면 push하지 않고 그 세션이나 사람에게 먼저 묻는다. push는 남의 커밋도 함께 올리고, 배포가 붙은 브랜치면 바로 나간다.
- 맨 `git stash`를 쓰지 않는다.
- 커밋 메시지는 스크래치패드 파일에 써서 `-F`로 준다. `.git/COMMIT_EDITMSG`는 남의 메시지일 수 있다.
- 앞 세션의 일을 이어받으면 `git log`·`git diff`로 끝난 것을 다시 확인한다.

## 6. 새 기능 점검표

새 기능은 다른 기능과 이어져야 한다. 새 기능 계획에는 아래에서 다른 기능과 이어지는 곳만 적고, 없으면 없다고 쓴다. 이어야 할 곳이 보이면 같은 범위로 할지 한 줄로 묻는다. 층·부품 목록은 project.md에 있다. 화면이 있는 프로젝트는 `docs/web.md` 2절의 질문을 더한다.

| # | 질문 |
|---|---|
| 1 | 새 개념·이름이 생기거나 뜻이 바뀌는가? (`GLOSSARY.md`) |
| 2 | 이미 있는 부품을 조합해서 만들 수 없나? |
| 3 | 새로 저장하는 사실이 있나? 이미 있는 사실에서 계산할 수 없나? 그 사실의 주인은 어디인가? 쓸 데이터가 지금 쌓이고 있나? |
| 4 | 저장 구조가 바뀌나? |
| 5 | 어느 층의 일인가? 아래층이 위층을 부르게 되지 않나? |
| 6 | 새 키·토큰·환경 변수가 필요한가? 없으면 조용히 꺼지나? |
| 7 | 실패할 지점이 있나? 실패가 사람이 보는 곳(오류 기록·알림·화면 문장)으로 가나? |
| 8 | 개인정보를 새로 저장·노출하나? 그 사람을 지우면 따라 지워지나? 남겨야 하는 기록은 사람 칸만 비워 남기나? |
| 9 | 다른 모듈이 원천인 기록을 그 원천 모듈로만 읽고 쓰나? |
| 10 | 누가 보고 고칠 수 있나? |
| 11 | 두 사람이 같은 값을 동시에 고칠 수 있나? |
| 12 | 이미 있는 기능과 같은 일을 하나? 대체 표를 썼나? |
| 13 | 어떻게 확인할 것인가? |
| 14 | 이 변경으로 어긋나는 문서가 있나? |

두 번째 알림 목록, 같은 사실의 두 번째 저장, 사람이 값을 베껴 옮기는 흐름은 만들지 않는다. 사람이 개입할 곳은 이미 있는 곳에 둔다.

## 7. 버그는 `/fix`로 고친다

`/fix` 스킬이 순서(재현 → 처음 잘못된 결정 → 사실의 주인 확인 → 두 안 → 고치기)를 묶는다. 코드를 고치기 전에 그 답을 먼저 적는다.

막힐 때:

- 원인을 나누기 전에 같은 명령을 다시 돌리지 않는다. 같은 오류가 많으면 환경부터 의심한다.
- 같은 전제의 고침이 두 번 실패하면 세 번째 전에 그 전제를 한 문장으로 적고 직접 시험한다.
- 같은 단계가 두 번 막히면 멈추고 사용자에게 한 줄로 알린다.

## 8. 문서 쓰는 규칙

- 규칙 문서에는 지금 규칙만 쓴다. 날짜, "예전에는", 경위, 시점에 따라 바뀌는 개수를 쓰지 않는다. 설계 초안은 상태와 날짜를 적어도 된다.
- 한 사실은 한 곳에 쓴다. 다른 문서가 맡는 내용은 그 문서를 가리키는 한 줄로 끝낸다. 어디에 쓸지는 `CLAUDE.md` "문서 지도"를 따른다.
- 어느 프로젝트에나 맞는 규칙은 dev-env 틀 문서에, 이 프로젝트에만 맞는 값은 project.md에 쓴다. 틀 문서를 이 저장소에서 고치면 다음 `setup.sh`가 덮어쓴다. 틀 문서를 고칠 일이면 dev-env 저장소에서 고친다.
- 코드·설정이 정답을 가지면 값을 옮기지 않고 그 파일을 가리킨다.
- 파일·함수·표 이름은 코드 글꼴로 쓰고, 적기 전에 `ls`·`grep`으로 지금 있는지 확인한다.
- 결정을 바꾸지 않는 문장은 지운다. 지시는 "~한다"/"~하지 않는다"로 쓴다.
- 한 대상은 한 이름으로 부른다(`GLOSSARY.md`).
- 규칙 문서에는 결과 규칙만 쓴다. 이유는 남길 가치가 있을 때만 결정 기록(9절)에 쓴다.
- `CLAUDE.md`는 짧게 둔다. 세부는 다른 문서에 쓰고 한 줄로 가리킨다.
- 같은 실수가 두 번이면 글보다 높은 장치로 막는다. 순서는 구조(길을 하나로) → 타입 → 검사·훅 → 테스트 → 글.

## 9. 결정 기록과 용어집

`domain-modeling` 스킬이 만든다.

- **용어집**: 저장소 맨 위 `GLOSSARY.md`. 한 대상 한 이름, 쓰지 않는 말도 적는다.
- **결정 기록**: `docs/adr/NNNN-<슬러그>.md`(번호는 차례대로). 1~3문장(무엇을, 왜). 고려한 대안은 버린 이유가 뻔하지 않을 때만 쓴다.
- 남기는 기준은 셋 다일 때다: 되돌리기 어렵다, 맥락 없이 보면 놀랍다, 실제 대안 사이에서 골랐다.
- 결정은 고치지 않는다. 바뀌면 새 장을 더하고, 옛 장 맨 위에 `대체됨: NNNN`만 적는다.

## 10. 규칙과 정면으로 어긋나면 멈추고 묻는다

문서가 "이렇게 한다/하지 않는다"고 쓴 것과 반대로 가야 하면 진행하지 않고 묻는다. 문서가 정하지 않은 취향 차이는 충돌이 아니다.

- 질문에 넣는 것: 규칙 문장 인용, 어디서 어긋나는지, 선택지 셋(원칙을 지키는 대안 / 이번만 예외 / 규칙을 고친다).
- 사용자가 같은 대화에서 그 예외를 이미 지시했으면 다시 묻지 않는다.
- 예외가 반복될 것 같으면 규칙이 틀린 것이다. 규칙 문서를 지금 맞는 내용으로 고치고 옛 문장을 지운다.
- 훅이 막은 일을 훅을 끄거나 우회해서 하지 않는다. 막힌 이유를 보고한다.
