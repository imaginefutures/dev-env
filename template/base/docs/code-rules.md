# 코드 설계 규칙

어느 언어·어느 프로젝트에나 쓰는 코드 규칙이다. 프로젝트마다 다른 값(층 순서, 기술 선택)은 [project.md](project.md), TypeScript·SQL DB를 쓰는 웹 서비스의 세부 규칙은 `web.md`가 맡는다. 일하는 순서는 [CONTRIBUTING.md](../CONTRIBUTING.md), 설계 용어(모듈·인터페이스·경계)는 `codebase-design` 스킬을 따른다.

## 1. 사실의 주인

- 한 사실은 한 곳에만 저장한다. 다른 곳에서 필요하면 계산한다.
- 저장해야 하는 파생값은 한 관문이 맞춰 저장한다. 여러 곳이 각자 맞추지 않는다.
- 숫자·상태는 한 곳(DB 뷰나 규칙 파일 하나)에서 정하고 화면은 읽기만 한다.
- 같은 계산이 필요하면 주인 파일 하나를 정하고 나머지는 그 함수를 부른다. 다른 곳에 다시 구현하지 않는다.
- 사실과 주인은 목록으로 두고, 주인 밖에서 같은 계산 모양이 나오면 테스트가 실패하게 한다.
- 화면·폼은 대상의 id를 든다. 값을 복사해 뒀다가 통째로 되쓰지 않는다.
- 서로 가리키는 데이터는 저장소가 참조를 지켜 주는 구조(표와 외래 키)로 둔다. 통째로 저장한 덩어리(JSON 한 칸) 안에 참조를 숨기지 않는다.

## 2. 부르는 방향

- 층 사이 부르는 방향은 한쪽으로만 둔다. 아래층이 위층을 부르지 않는다. 층 순서는 project.md.
- 모듈 바깥에서는 그 모듈의 입구 파일만 부른다. 속 파일을 바로 부르지 않는다.
- 이 둘은 글이 아니라 의존 검사 도구로 막는다.

## 3. 순수 규칙 파일과 요청 처리

- 저장소 없이 정할 수 있는 규칙(검사·날짜·상태 결정·보낼지 판단)은 순수 파일에 두고 단위 테스트로 확인한다. 새로 만들기 전에 있는 규칙 파일을 찾는다.
- 요청 처리 코드는 "확인 → 규칙 호출 → 저장"만 한다. 라우트·반복 작업 루프·쿼리 안에 규칙을 두지 않는다.
- 바깥 값(요청 본문·외부 응답·웹훅·파일·환경 변수)은 입구에서 한 번 검사·정리한다. 검사 규칙은 한 곳이고, 저장하는 곳과 보여 주는 곳이 같은 함수를 쓴다.
- 함께 맞춰야 하는 참/거짓 값 둘 대신 상태 값 하나를 둔다. 종류별 값은 종류를 키로 한 표 하나에 모은다.
- 만드는 길은 하나다. 같은 종류를 새로 만드는 코드는 한 파일에만 있다.

## 4. 두 번 돌아도 안전하게

상태를 바꾸는 일(외부 호출·웹훅·예약 작업·데이터 옮기기·저장 구조 변경)은 "두 번 돌면? 중간에 죽으면? 남은 표시를 다음 실행이 낡았다고 알아보나?"에 답한다.

| 일 | 장치 |
|---|---|
| 되돌릴 수 없는 외부 호출(발송·결제) | 호출 전에 유일 키로 장부 줄을 먼저 잡는다. 응답 없이 남은 줄은 정한 시간이 지난 것만 외부 조회로 확정한다 |
| 대상 × 단계로 도는 처리 | 대상 × 단계마다 유일 제약을 두고, 기록을 먼저 만들고 실행한다 |
| 예약 작업 | 작업마다 임대 기한(lease)을 쥔다. 실행하던 쪽이 죽으면 기한이 지난 뒤 다른 쪽이 이어받는다 |
| 저장 구조 변경 | 변경 하나 = 트랜잭션 하나. 같은 트랜잭션에서 적용 기록을 남긴다 |
| 데이터 옮기기 스크립트 | 몇 번을 다시 돌려도 결과가 같다. 기본은 확인만 하고, `--apply`일 때만 쓴다. 옮기기 전 건수와 뒤 건수를 대조한다 |
| 읽고 쓰기 묶음 | 트랜잭션 안에서 잠금을 먼저 잡는다 |

메모리 플래그나 "읽은 뒤 쓰기"로 한 번만을 지키지 않는다. "처리 중" 표시에는 시각·만료·주인을 같이 남긴다.

## 5. 권한 경계

- 사용자·팀 사이의 데이터 경계는 가능하면 앱 코드가 아니라 저장소가 막는다. 방법은 project.md.
- 경계를 넘는 읽기(로그인, 주소로 대상 찾기, 다른 소속 확인)는 그 사람·키로 좁힌 쿼리 하나만 경계 밖 권한으로 돈다. 빠뜨리면 오류 없이 0건이 되어 화면이 비거나 "없음" 확인이 거꾸로 통과한다.
- 경계 정보 없이 도는 쿼리는 테스트에서 오류로 만든다.
- "하나만 있어야 하는" 관계는 저장소 제약으로 막는다. 코드가 "첫 번째 것"을 짐작해서 고르지 않는다.

## 6. 저장 구조 바꾸기

- 저장 구조는 기록이 남는 마이그레이션 파일로만 바꾼다.
- 칸을 더하기 전에 같은 사실이 이미 저장되는 곳이 없는지 본다.
- 운영 중인 구조의 삭제·이름 바꾸기는 두 번에 나눈다(먼저 코드에서 빼고, 다음 배포에서 지운다). 방법은 `deprecation-and-migration` 스킬의 넓혔다 좁히기(expand/contract).

## 7. 테스트

- 테스트는 동작을 깨면 실패하고 속만 바꾸면 통과해야 한다. 기대값은 코드를 돌린 출력이 아니라 요구에서 낸다(`tdd` 스킬).
- 층을 먼저 정한다. 계산·판단은 순수 규칙의 단위 테스트, 권한·저장·트랜잭션은 저장소를 붙인 테스트, 여러 단계를 거치는 사용자 흐름만 끝에서 끝까지(e2e) 테스트다.
- 테스트 파일 이름은 이슈 번호가 아니라 모듈과 동작 이름으로 짓는다. 같은 흐름의 테스트가 있으면 새 파일을 만들지 않고 단계를 더한다.
- 테스트끼리 저장소·포트를 같이 쓰지 않는다. 테스트마다(또는 실행마다) 자기 DB와 빈 포트를 받는다.
