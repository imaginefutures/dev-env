# /fix: 근본 원인으로 고치는 한 입구

코드를 한 줄 고치기 전에 아래 1~4를 답으로 먼저 적는다. 일하는 순서 전체는 `CONTRIBUTING.md` "버그는 /fix로 고친다", 사실의 주인은 `docs/code-rules.md` "사실의 주인"이다.

## 1. 재현과 증거

로그·기록 표·로컬 재현으로 증상을 직접 만든다. 사용자에게 재현을 부탁하지 않는다. 못 만들면 "재현 못 함"이라 쓰고 멈춘다. 추측으로 고치지 않는다.

가설을 적고 실제 동작으로 하나씩 지운다. 틀린 가설로 넣은 코드는 되돌린다.

## 2. 처음 잘못된 결정

"왜?"를 **코드의 결정**이 나올 때까지 묻는다. 답이 "앞 단계 값이 이상해서"면 아직 아니다. 다음 둘 중 어디인지 적는다.

- 그 상태가 정당하다 → 그 상태에서 깨진 코드가 원인
- 있으면 안 되는 상태다 → 그 상태를 만든 곳이 원인

## 3. 사실의 주인 확인 (여기서 땜질이 갈린다)

이 증상은 **같은 사실을 둘 이상의 곳이 따로 계산해서** 어긋난 것인가?

1. 사실의 주인 목록이 있으면 이 사실이 거기 있나 본다.
2. 없으면 같은 계산(같은 칸·같은 조건·같은 상수)을 하는 곳을 **전부** 찾는다. `graphify-out/graph.json`이 있으면 `graphify query`·`graphify affected`로 먼저 찾고, 없으면 `grep`으로 찾는다. 명령과 찾은 수를 적는다.
3. 둘 이상이면 이 버그의 근본은 "주인이 없다"이다. 고침은 한 곳을 주인으로 정하고 나머지를 그 호출로 바꾸는 것이다.
4. `git log --oneline -- <파일>`에서 이 파일의 fix 커밋이 잦으면 같은 자리를 또 만지는 것이다. 이전 fix 커밋 제목을 읽고 같은 뿌리인지 본다.

## 4. 두 안을 적고 권장안으로 묻는다

고침이 아래 모양이면 **봉합 신호**다.

- 그 자리에서 값을 자르거나 기본값으로 덮는다
- 막는 검사(guard)·재시도·삼킨 오류를 더한다
- 증상이 보인 화면에서만 고친다
- 같은 계산을 한 곳 더 복사한다

봉합 신호가 하나라도 있으면 **최소안(봉합)**과 **근본안(구조)**을 둘 다 적는다. 각각 바뀌는 파일 수, 다시 터질 조건, 비용을 쓰고 권장안에 표시해 묻는다. 사용자가 최소안을 고르면 커밋 본문에 "봉합: 근본안은 <어디에 적었는지>"를 남긴다.

신호가 없고 근본안이 작으면 묻지 않고 근본안으로 간다.

## 5. 고치기

- 순수 규칙 파일로 닿으면 실패하는 테스트를 먼저 쓴다(`tdd` 스킬).
- 주인을 새로 정했으면 사실의 주인 목록에 한 줄 더한다(목록이 없으면 이번에 만든다). 그래야 다음에 같은 계산이 다시 생기면 테스트가 실패한다.
- 3번에서 찾은 곳을 같은 커밋에서 모두 고친다.

## 끝났다고 하려면

원래 재현이 같은 환경에서 통과했고, 3번의 검색 명령과 결과 수가 커밋 본문에 있고, 봉합이라면 근본안이 어디에 적혔는지가 있다.
