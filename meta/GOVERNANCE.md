# 체계 관리

dev-env를 고치는 모든 작업이 먼저 읽는다. 이 폴더(`meta/`)는 새 프로젝트에 깔리지 않는다(`setup.sh`가 지운다).

Claude는 체계를 키우는 사람이 아니라 지키는 사람이다. 규칙을 더하는 것은 비용이다. 뿌리는 [ROOT.md](ROOT.md)다.

## 1. 문제가 생기면 진단부터 한다

위에서부터 처음 해당하는 단계에서 멈춘다.

0. 항상: 사건을 `cases/`에 사례로 남긴다(입력, 나온 결과, 맞는 결과). 사례는 규칙을 건드리지 않는다.
1. 해당 규칙이 이미 있었는데 안 지켜졌나 → 규칙을 더하지 않는다. 왜 안 지켜졌는지(안 보임, 모호함, 다른 규칙에 밀림)를 고친다.
2. 기존 규칙이 모호하거나 틀렸나 → 그 규칙을 고쳐 쓴다.
3. 두 규칙이 충돌했나 → 뿌리에 비춰 이길 쪽을 정하고 진 쪽을 고치거나 지운다.
4. 정말 빈 곳인가 → 2절 통과 조건을 모두 넘어야 규칙이 된다.
5. 처음 일어난 일인가 → 규칙을 만들지 않는다. 사례로 두고 같은 구조가 다시 나오면 4로 간다.

## 2. 새 규칙의 통과 조건 (하나라도 못 넘으면 반려)

- **일반화:** 사건을 지우고 "어떤 종류의 실패인가"를 한 문장으로 쓴다. 사건의 고유한 이름·숫자·상황이 남으면 반려.
- **근거:** 서로 다른 사례 2개 이상이 같은 구조여야 한다. 하나뿐이면 `가설`로 표시하고 만료 조건(날짜 또는 사용 횟수)을 붙인다. 만료까지 두 번째 사례가 없으면 지운다.
- **뿌리 연결:** 어느 원칙에서 내려오는지 한 줄.
- **범위:** 언제 적용되고 언제 적용되지 않는지 한 줄.
- **충돌·중복:** 같은 주제의 기존 규칙을 전부 읽는다. 겹치면 합치고, 부딪히면 1절 3번으로 간다.
- **더 싼 방법 먼저:** (a) 기존 규칙 삭제·단순화 (b) 자동 검사 (c) 기본값 변경을 문장보다 먼저 따진다.
- **총량:** 하나를 더하면 하나 이상을 합치거나 지워 총량이 늘지 않게 한다.

## 3. 도입 심사 (스킬·플러그인·도구·외부 규칙)

후보를 들이기 전에 아래를 지난다. 기록 없이 들이지 않는다.

1. 어떤 일을 맡나? dev-env에 그 일이 비어 있나? 비어 있지 않으면 여기서 멈춘다.
2. 기존 스킬과의 관계를 스킬마다 한 줄로 쓴다: 중복(안 받음) · 대체(옛것을 뺀다) · 충돌(하나만 둔다) · 보완(순서를 정한다) · 무관.
3. 뿌리 P1~P5를 하나씩 대 본다.
4. 소유권: `DESIGN.md`, `CLAUDE.md`, `settings.json`을 직접 쓰거나 고치나? 밖으로 데이터를 보내나?
5. 설치하지 않고 원본을 읽는다. 안의 스크립트는 돌리지 않는다. 못 본 것(보안 평가 등)은 못 봤다고 적는다.
6. 판정을 `intake/<이름>.md`에 쓴다: **필수**(틀에 넣는다) · **선택**(깔려 있으면 쓴다) · **안 받음**. 이유와 다시 심사할 조건을 적는다.
7. 안 받은 것을 다시 꺼내면 이전 이유를 먼저 보이고, 새 사실이 있을 때만 다시 정한다.

## 4. 정기 가지치기 (변경 5개마다, 또는 월 1회)

- 규칙마다 "지우고 쌓인 사례를 다시 돌려" 아무것도 안 깨지면 지운다.
- 오래 쓰이지 않은 규칙은 복구 가능한 곳(git 이력)에 맡기고 지운다.
- 같은 종류 규칙이 3개 이상이면 상위 원칙 하나로 올리고 아래를 지운다.
- 세 숫자를 `changes.md` 맨 아래에 갱신한다: 규칙 수, 예외 문구("단, ~일 때는") 수, 가설 규칙 수. 처음 센 값이 기준선이다.

## 5. 다시 짓기 신호

아래 중 둘 이상이면 고치지 말고 뿌리와 사례에서 규칙을 새로 쓴다. 사례는 그대로 두고 새 규칙과 옛 규칙을 같은 사례로 비교해 나은 쪽을 쓴다.

- 규칙 수가 기준선의 2배를 넘었다.
- 예외 문구가 규칙의 20% 이상이다.
- 규칙을 설명하려고 규칙을 또 만들고 있다.
- 뿌리 원칙이 한 번이라도 어겨졌다.

## 6. 변경 기록

모든 변경은 [changes.md](changes.md)에 한 줄을 남긴다: 날짜 / 어떤 사례 / 진단 몇 번 / 더한 것과 뺀 것 / 총량 변화. 기록이 없는 변경은 하지 않은 것으로 본다.

## 7. 가설 규칙

### H1 세션 로그 (만료: 측정 5번 안에 합격선을 못 맞추면 폐기)

- **뿌리 연결:** P1(맥락이 끊겨 처음부터 다시 설명하는 절차를 없앤다).
- **범위:** 긴 세션이 압축될 때. 짧은 세션에는 쓰지 않는다.
- **규칙:** 세션 진행에 따라 `temp/session-log/<날짜>.md`에 로그를 남긴다. 남기는 단위는 git·코드에서 되살릴 수 없는 사실이다: 결정과 이유, 버린 안과 이유, 숫자·조건의 정확한 값, 확인한 것과 못 한 것, 열린 일. 되살릴 수 있는 것은 경로 한 줄만 쓴다.
- **문장 고르기:** 지우면 복원이 안 되는 항목을 가장 많이 덮는 문장부터 넣고, 새로 덮는 항목이 없는 문장은 버린다. 요약하려고 새로 쓴 문장도 같다.
- **측정(압축 직전과 마일스톤에서만):**
  1. 로그를 쓰기 전에, 로그를 쓰지 않는 다른 에이전트가 원문에서 질문 N개와 정답을 고정한다. 질문의 절반 이상은 "왜 그렇게 정했나", "무엇을 안 했나", "무엇을 확인 못 했나"로 한다.
  2. 원문 없이 로그만 읽는 새 에이전트가 k번 답한다.
  3. 합격: 정답률 평균 90% 이상, 회차끼리 같은 답을 낸 비율도 90% 이상.
  4. 틀린 질문마다 그것을 덮는 문장을 더한다. 합격하면 문장을 하나씩 빼 보고 점수가 안 떨어지는 문장은 지운다.
- k=3~5와 "최저 회차 80% 이상"은 근거 없는 시작값이다. 처음 측정에서 조정한다.
- 압축 뒤 세션 시작 때 로그를 읽는 훅은 `settings.json`을 바꾸므로 따로 확정받고 넣는다. 아직 넣지 않았다.
